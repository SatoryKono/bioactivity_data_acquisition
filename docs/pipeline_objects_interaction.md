
# Взаимодействие между объектами пайплайна

## 1. Общая картина

Есть несколько слоёв, которые почти не взаимодействуют напрямую:

- **pipeline/** – оркестрация (`PipelineBase`, `StageABC`, хуки, CLI).
- **source/** – общение с внешним источником (request builder → client → parser → paginator).
- **processing/** – трансформации, обогащение, дедупликация, бизнес‑ключи, хэши, merge.
- **validation/** – схемы, валидация записей, агрегатные DQ‑правила.
- **output/** – стратегия путей, запись данных, метаданные.
- **utils/** – конфиг/секреты, кэш, логирование, трассировка, обработка ошибок, прогресс.

`pipeline_structure.md` фиксирует эту структуру каталогов.

---

## 2. Инициализация пайплайна

### 2.1. CLI и конфиг

1. Пользователь запускает реализацию **CLICommandABC**. Команда:
   - читает аргументы;
   - использует **ConfigResolverABC** для сборки итогового конфига из файлов, переменных окружения и CLI‑флагов;
   - при необходимости обращается к **SecretProviderABC** за секретами (токены, пароли и т.п.).

2. CLI создаёт экземпляр конкретного пайплайна, наследника **PipelineBase**, и передаёт туда `config` и `run_id`.

3. В конструкторе `PipelineBase`:
   - создаётся структурированный логгер через **LoggerAdapterABC**;
   - инициализируются **TracerABC** и **ProgressReporterABC** (часто через `PipelineHookABC`);
   - создаётся реестр внешних клиентов (БД, HTTP и т.п.), которые будут корректно закрыты в конце.

Результат: объект пайплайна с привязанным конфигом, логированием, трассировкой и доступом к секретам.

---

## 3. Оркестрация: `PipelineBase.run` и стадии

Метод `PipelineBase.run(output_path, dry_run=False, …)` реализует общий сценарий:

> `extract → transform → validate → write`

Шаги:

1. Логирует старт, фиксирует время.
2. Последовательно вызывает:
   - `extract(...)`
   - `transform(df)`
   - `validate(df)`
   - `write(df, output_path)` (если не `dry_run`).
3. Для каждой стадии измеряет длительность, считает строки, отправляет показатели в логгер, трассер и прогресс‑репортер.
4. В `finally` вызывает `close_resources()`, который закрывает все зарегистрированные клиенты.

**StageABC** – общий интерфейс для стадий конвейера над потоками. Он может использоваться:
- внутри `transform`;
- поверх `PipelineBase` для более сложных сценариев.

Каждая стадия принимает `Iterable[In]`, отдаёт `Iterable[Out]` и не знает о других стадиях.

`PipelineHookABC` получает уведомления о начале/конце пайплайна и каждой стадии, а также об ошибках. Хуки реализуют логирование, метрики, алерты, но не принимают бизнес‑решений.

## 4. Взаимодействие со внешним источником (extract)

Типичный `extract` собирается из абстракций в `source/`:

1. **RequestBuilderABC**
   - По конфигу и (опционально) времени запуска строит стартовый запрос `build_initial()`.
   - По курсору или номеру страницы строит последующие запросы `build_for_page(cursor)`.

2. **PaginatorABC**
   - Получает стартовый `RequestT` от `RequestBuilderABC`.
   - По `ResponseT` вычисляет следующий `RequestT` (offset/limit, cursor, token).
   - Сам запросы не отправляет, только генерирует последовательность `RequestT`.

3. **SourceClientABC**
   - Принимает `RequestT`, отправляет его во внешний сервис и возвращает `ResponseT`.
   - Перед отправкой:
     - вызывает `RateLimiterABC.acquire()`;
     - при ошибках использует **RetryPolicyABC** (`should_retry(attempt, error)`, `get_backoff_seconds(attempt)`).
   - В `finally` вызывает `RateLimiterABC.release()`.

4. **ResponseParserABC**
   - Из `ResponseT` извлекает поток доменных объектов `ParsedItemT`: `parse_items(response)`.
   - Извлекает курсор `extract_cursor(response)`, который передаётся `PaginatorABC` / `RequestBuilderABC.build_for_page()`.

5. Весь стек может быть обёрнут в **StageABC**, которая:
   - на вход получает пустой вход или параметры диапазона;
   - внутри крутит цикл: `build_request → client → parser → paginator`;
   - на выход отдаёт поток сырых записей.

Ошибки транспорта (таймауты, 5xx, сетевые) обрабатывает клиент, используя `RetryPolicyABC`. Решение о том, заваливать ли пайплайн или пропускать элементы, принимает уровень выше через **ErrorPolicyABC** и оркестратор.

## 5. Обработка данных (transform)

После `extract` данные попадают в `transform`. В базовом `PipelineBase` это DataFrame, но внутри можно использовать цепочку `StageABC` над потоками.

Типичная цепочка:

1. **TransformerABC**
   - Для каждой записи `RecordT` выполняет детерминированное преобразование в нормализованный `ValidatedRecordT`.
   - Делает приведение типов, нормализацию структур.
   - Не выполняет I/O и не меняет объём данных.

2. **SideInputProviderABC** + **LookupEnricherABC**
   - `SideInputProviderABC` загружает и предоставляет `Mapping[SideKeyT, SideValueT]` из файлов/БД/HTTP/кэша.
   - `LookupEnricherABC` использует запись и сайд‑инпуты для обогащения записи справочными значениями (коды, классификаторы, маппинги).

3. **CacheABC**
   - Может использоваться:
     - внутри `SideInputProviderABC`;
     - внутри `TransformerABC` / `LookupEnricherABC`.
   - Позволяет не обращаться к внешнему источнику повторно по одному и тому же ключу.
   - Живёт в рамках одного запуска и не является источником истины.

4. **BusinessKeyDeriverABC** + **DeduplicatorABC** + **MergeStrategyABC** + **HasherABC**
   - `BusinessKeyDeriverABC` вычисляет бизнес‑ключ записи (устойчивый, хэшируемый, без технических ID).
   - `DeduplicatorABC` получает поток записей и `key_fn` и возвращает поток без дублей по бизнес‑ключу (либо с ограниченным числом дублей).
   - `MergeStrategyABC` объединяет несколько записей с одним ключом в одну с учётом приоритетов источников, дат, качества и т.п.
   - `HasherABC` считает хэши:
     - по всей записи;
     - по бизнес‑ключу.
   Хэши используются для контроля целостности, идемпотентности и в метаданных.

Всё это удобно реализовать как последовательность `StageABC`, где каждая стадия принимает `Iterable` и возвращает `Iterable`, а `transform` запускает мини‑конвейер и по необходимости собирает результат в DataFrame.

## 6. Валидация и контроль качества

Компоненты из `validation/` обеспечивают два уровня проверки: на уровне отдельной записи и на уровне набора.

### 6.1. Схема и проверка отдельных записей

1. **SchemaProviderABC**
   - По профилю/версии/типу данных выдаёт объект схемы `SchemaT`.

2. **ValidatorABC**
   - Принимает запись `RecordT` и `SchemaT`, возвращает `ValidationResult[RecordT]`.
   - `ValidationResult` содержит:
     - `record` (скорректированную запись или `None`, если запись неприемлема);
     - набор `ValidationError` (поле, сообщение, код).

3. `PipelineBase.validate`
   - Получает схему (через `SchemaProviderABC` или из собственного свойства).
   - Прогоняет DataFrame через схему (например, через Pandera).
   - Может добавлять хэш‑колонки для идентификации строк.

Таким образом, есть:
- "твёрдая" схема на уровне DataFrame;
- более гибкая логика на уровне RecordT через `ValidatorABC`.

Они могут использоваться по отдельности или совместно.

### 6.2. Агрегатные DQ‑правила

1. **DQRuleABC**
   - Работает на уровне набора записей (потока).
   - Ищет дубликаты, пропуски в диапазонах, нарушения референциальной целостности и другие агрегатные аномалии.
   - Не изменяет сами данные.

2. **DQIssue**
   - Результат работы DQ‑правил: какое правило сработало и сколько записей затронуто.
   - Используется для отчётов и мониторинга качества.

3. **ProgressReporterABC**
   - Собирает статистику по стадиям:
     - сколько извлечено;
     - сколько прошло валидацию;
     - сколько и по какой причине отброшено.

Решение о прерывании запуска из‑за низкого качества принимается на уровне пайплайна, на основе `DQIssue` и отчётов `ProgressReporterABC`, а не внутри `ValidatorABC` / `DQRuleABC`.

## 7. Запись данных и метаданных

Компоненты из `output/`:

1. **PathStrategyABC**
   - По partition‑контексту (например, дата, источник, версия) строит `Path`, куда будет записан артефакт.
   - Не пишет сам, только определяет layout на файловой системе или в S3.

2. **WriterABC**
   - Принимает `Iterable[RecordT]` и `Path`.
   - Пишет данные в нужном формате (CSV, Parquet и т.п.).
   - Обеспечивает атомарность: либо успешный артефакт, либо ошибка без "подбитых" файлов.

3. **MetadataWriterABC**
   - Принимает `Path` артефакта и объект метаданных `MetadataT`.
   - Пишет отдельный служебный файл (JSON/YAML), содержащий:
     - `run_id`;
     - имя пайплайна;
     - количество строк;
     - хэши;
     - версию схемы, источник;
     - длительности стадий и прочие параметры.

4. `PipelineBase.write`
   - Может реализовывать:
     - сортировку по колонкам;
     - атомарную запись временный_файл → rename;
     - создание файла метаданных.

`PathStrategyABC`, `WriterABC` и `MetadataWriterABC` могут использоваться и самостоятельно, без `PipelineBase`, в пайплайнах на основе `StageABC` и потоков.

---

## 8. Ошибки, ретраи, телеметрия

### 8.1. Ошибки и ретраи

Два уровня:

1. **RetryPolicyABC**
   - Отвечает на вопросы:
     - повторять ли транспортный запрос;
     - через сколько секунд выполнить повтор.
   - Используется в `SourceClientABC` вокруг непосредственного вызова внешнего сервиса.

2. **ErrorPolicyABC + ErrorAction**
   - На уровне пайплайна принимает решение, что делать с исключениями:
     - повторить операцию;
     - пропустить элемент;
     - завершить пайплайн с ошибкой.
   - Возвращает `ErrorAction`, который оркестратор интерпретирует (повторить стадию, пропустить элемент или прервать run).

`RetryPolicyABC` отвечает за транспортный уровень, `ErrorPolicyABC` – за поведение пайплайна в целом.

### 8.2. Логирование и трассировка

- **LoggerAdapterABC** – единый интерфейс логирования, через который пишут все стадии и пайплайны.
- **TracerABC** – собирает тайминги и счётчики, может оборачивать стадии или внешние вызовы в span’ы.
- **PipelineHookABC** – точка подключения логирования, метрик и алертов к событиям жизненного цикла пайплайна.

Бизнес‑код не зависит от конкретной системы логирования или метрик, он работает через абстрактные адаптеры.

---

## 9. Жизненный цикл пайплайна: сквозной сценарий

Сценарий целиком:

1. **CLICommandABC**
   - собирает конфиг через `ConfigResolverABC` + `SecretProviderABC`;
   - создаёт наследника `PipelineBase` с `run_id`.

2. `pipeline.run(output_path, dry_run=…)`
   - логгер, трейсер и хуки получают событие `pipeline_started`.

3. `extract()`
   - `RequestBuilderABC.build_initial()` → первый `RequestT`;
   - `PaginatorABC` / `StageABC` циклически выполняет:
     - `RateLimiterABC.acquire()`;
     - `SourceClientABC.send(request)` с использованием `RetryPolicyABC`;
     - `ResponseParserABC.parse_items(response)` → поток `ParsedItemT`;
     - `ResponseParserABC.extract_cursor(response)` → курсор для следующего запроса.
   - результат: поток или DataFrame сырых записей.

4. `transform(df)`
   - конвейер `StageABC`:
     - `TransformerABC`: приведение типов и нормализация;
     - `SideInputProviderABC` → `LookupEnricherABC`: обогащение;
     - `BusinessKeyDeriverABC` → `DeduplicatorABC` + `MergeStrategyABC`: консолидация;
     - `HasherABC`: хэши записей/ключей.
   - `ProgressReporterABC` фиксирует, сколько записей осталось после трансформации.

5. `validate(df)`
   - `SchemaProviderABC` / встроенная схема → `ValidatorABC` → `ValidationResult` + `ValidationError`;
   - отбрасывание некорректных записей, расчёт `DQIssue` на уровне набора;
   - `ProgressReporterABC` фиксирует валидные и отброшенные записи.

6. `write(df, output_path)` (если не `dry_run`)
   - `PathStrategyABC` выдаёт путь по partition‑контексту;
   - `WriterABC` записывает данные (атомарно);
   - `HasherABC` при необходимости считает хэш файлов/партиций;
   - `MetadataWriterABC` записывает метаданные о запуске и артефакте.

7. `run` формирует итоговый результат запуска (`RunResult`), закрывает все клиенты через `close_resources()`, хуки получают событие `pipeline_finished`.

Таким образом, взаимодействие объектов строится вокруг чётких контрактов по слоям, минимальных связей между ними и одного оркестратора (`PipelineBase` или композиции `StageABC`), который связывает всё в единый конвейер.
