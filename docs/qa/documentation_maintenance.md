# План поддержки документации

Документ фиксирует процессы обновления документации, чтобы описания архитектуры
и публичного API оставались синхронизированными с кодом.

## Цели

1. Каждое изменение публичного интерфейса (`PipelineBase`, `UnifiedPipelineBase`,
   `ChemblPipelineBase`, CLI-команды) сопровождается обновлением релевантных
   файлов (`README.md`, `docs/architecture.md`, профильные статьи в
   `docs/pipelines/`).
2. Все артефакты, перечисленные в `docs/INDEX.md`, остаются актуальными и
   доступны через единый оглавление.
3. Вкладчики получают понятный чек-лист и автоматическую проверку в CI.

## Рабочий процесс

1. **Перед разработкой** — уточнить, какие разделы затрагиваются
   (архитектура, CLI, конфиги) и добавить задачу по документации в PR-план.
2. **Во время разработки** — обновлять docstring’и и Markdown параллельно с кодом;
   в идеале, до мерджа не должно оставаться TODO по документации.
3. **Перед мерджем** — пройти чек-лист:
   - README и профильные документы не содержат устаревших сигнатур;
   - ссылки в `docs/INDEX.md` ведут на актуальные файлы;
   - для новых модулей добавлены соответствующие разделы в `docs/pipelines/`.
4. **После релиза** — если публичный API менялся, добавить заметку в CHANGELOG и
   обновить примеры CLI/конфигов.

## Интеграция с CI

- Workflow `qa` (см. `Makefile` цели `qa` и `docs-lint`, если будет добавлена)
  должен выполнять `mkdocs build --strict` или, как минимум, `python -m
  markdownlint_cli docs/` (выбирается в зависимости от доступных инструментов).
- Скрипт `scripts/check_output_artifacts.py` можно дополнить проверкой, что все
  файлы из `docs/INDEX.md` существуют; аналогичную проверку стоит добавить в
  `pytest` (легковесный smoke-test).
- Для docstring’ов использовать `ruff` (`pydocstyle` правила) и `mypy --strict`
  на ключевых модулях, чтобы сигнатуры в документации совпадали с кодом.

## Ответственность

- **Автор PR** — обновляет документацию и описывает изменения в разделе
  `Summary` Pull Request’а.
- **Reviewer** — проверяет ссылки, соответствие инструкций CLI/конфигов и
  наличие примеров.
- **Tech writer / архитектор** — периодически (не реже одного раза в квартал)
  проводит ревизию `docs/` и README, синхронизируя их с реальной структурой
  пакетов.

## Дополнительные рекомендации

- Использовать единый стиль оформления (см.
  `docs/styleguide/10-documentation-standards.md`).
- При добавлении новых файлов сразу регистрировать их в `docs/INDEX.md` и, при
  необходимости, в `mkdocs.yml`.
- Документы, описывающие архитектуру, должны содержать ссылку на релевантные
  тесты (например, `tests/bioetl/pipelines/chembl/common/test_descriptor_runner.py`).
