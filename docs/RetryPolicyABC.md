# RetryPolicyABC

## Назначение

`RetryPolicyABC` задаёт стратегию повторных попыток при ошибках на транспортном уровне.  
Это **не** код, который делает `sleep` и выполняет запрос заново, а чистая политика, отвечающая на вопросы:

- «Нужно ли повторять попытку?»  
- «Если нужно, через сколько секунд?»

## Общее представление интерфейса

```python
from typing import Protocol

class RetryPolicyABC(Protocol):
    def should_retry(self, attempt: int, error: Exception) -> bool:
        """Решить, следует ли выполнять ещё одну попытку."""
        ...

    def get_backoff_seconds(self, attempt: int) -> float:
        """Вернуть длительность паузы перед следующей попыткой."""
        ...
```

## Модель попыток

Типичная нумерация:
- `attempt = 0` — первая попытка (без ретраев),
- `attempt = 1` — первый retry,
- `attempt = 2` — второй retry,
- и так далее.

Политика должна быть **детерминированной** относительно `(attempt, error)`.  
Случайность (джиттер) реализуется вне `RetryPolicyABC` при вычислении фактического `sleep`.

## Методы

### `should_retry(self, attempt: int, error: Exception) -> bool`

Назначение: решить, нужно ли выполнять ещё одну попытку.

Требования:
- Опирается только на входные параметры (`attempt`, `error`) и своё конфигурированное состояние.
- Может учитывать:
  - тип исключения,
  - его атрибуты (например, HTTP‑код),
  - максимальное количество попыток.

Инвариант:
- Если для некоторой пары `(attempt, error)` возвращено `False`, то дальнейшие вызовы с **тем же типом ошибки** и **большим `attempt`** обычно также должны возвращать `False` (достигнут лимит).

### `get_backoff_seconds(self, attempt: int) -> float`

Назначение: задать длительность ожидания перед следующей попыткой.

Требования:
- Возвращаемое значение:
  - неотрицательное,
  - может быть `0` (повтор сразу),
  - может возрастать с номером попытки.
- Не должно зависеть от глобального состояния пайплайна, только от `attempt` и конфигурации политики.

## Типичные политики

1. **Фиксированная**
   - Повтор до `max_attempts` при «транзитных» ошибках (таймауты, HTTP 5xx и пр.).
   - Постоянная пауза `fixed_delay`.

2. **Экспоненциальный backoff**
   - Пауза `base * 2**attempt`.
   - Опционально: ограничение максимальной задержки (`max_delay`).

3. **Комбинированные стратегии**
   - Разные лимиты и задержки для разных типов ошибок:
     - сетевые сбои,
     - лимиты времени,
     - перегрузка источника.

## Взаимодействие с другими компонентами

- **`SourceClientABC`**:
  - инициализирует `attempt = 0`,
  - при ошибке:
    - вызывает `should_retry`,
    - при `True` берёт задержку из `get_backoff_seconds`,
    - выполняет фактический `sleep` и повторяет отправку.
  - `RetryPolicyABC` не должен содержать IO и не знать о механизме ожидания.

- **`ErrorPolicyABC`**:
  - работает уровнем выше и решает:
    - пропустить запись,
    - повторить часть пайплайна,
    - завалить весь pipeline.
  - `RetryPolicyABC` — только транспортный слой.

## Инварианты

- Нет глобальных счётчиков попыток на уровне пайплайна, влияющих на поведение политики: решение должно полностью определяться `(attempt, error)` и конфигурацией.
- `get_backoff_seconds` никогда не возвращает отрицательное значение.

## Ошибки использования

- Встраивание в `RetryPolicyABC` логики бизнес‑ретраев  
  (например, ожидание изменения состояния доменной сущности в API) требует дополнительного контекста и должно быть оформлено отдельным уровнем логики.
- Привязка политики к «глобальному» числу ошибок по всему пайплайну нарушает локальность и сильно усложняет тестирование.
