# Базовый класс `bioetl.core.PipelineBase`

## 1. Назначение и место в архитектуре

`bioetl.core.PipelineBase` — абстрактный базовый класс для всех **табличных** ETL-пайплайнов проекта `bioetl`.  
Он инкапсулирует общий жизненный цикл обработки данных:

> `extract → transform → validate → write → run_result`

и отвечает за:

- единый интерфейс для всех табличных пайплайнов;
- оркестрацию стадий;
- логирование шагов и метрик времени;
- валидацию схемы данных на уровне `pandas.DataFrame`;
- атомарную запись результатов на диск;
- управление внешними ресурсами (клиенты БД, HTTP-клиенты и т.п.);
- поддержку режима `dry_run` (запуск без записи результатов).

Этот класс **не является** универсальной абстракцией над всеми возможными пайплайнами. Он реализует конкретный сценарий DataFrame-ориентированной обработки и живёт в прикладном слое `bioetl`.

В абстрактной библиотеке (`mypipeline/pipeline/...`) общая оркестрация может быть представлена другим `PipelineBase` и набором стадий `StageABC`. Табличный `bioetl.core.PipelineBase` следует рассматривать как специализированную реализацию того же концепта, а не как единственный возможный базовый класс.

## 2. Общие требования и зависимости

Класс объявляется в модуле `src/bioetl/core/pipeline_base.py` и наследуется от `abc.ABC`.

Он использует:

- `pandas` (`pd.DataFrame`) как основной табличный формат данных;
- `pandera` (`pa.DataFrameSchema`) для декларативной валидации структуры и типов данных;
- `structlog` для структурированного логирования;
- `pathlib.Path` для работы с файловой системой;
- стандартные модули `abc`, `dataclasses`, `time`, `typing`.

Связанные типы результатов (`WriteResult`, `RunResult`) определяются в модуле `src/bioetl/types.py` и импортируются в `pipeline_base.py`.

На уровне общей библиотеки валидация может описываться через:

- `SchemaProviderABC` — поставщик схем,
- `ValidatorABC` — применение схем к записям с выдачей `ValidationResult`.

В табличном слое `bioetl` эти абстракции реализуются через `pandera.DataFrameSchema` и логику `PipelineBase.validate`.

## 3. Конструктор и базовые свойства

```python
PipelineBase(config: PipelineConfig, run_id: str)
```

Обязательные аргументы:

- `config: PipelineConfig` — конфигурация конкретного пайплайна (источники, параметры обработки, опции вывода и т.п.);
- `run_id: str` — уникальный идентификатор запуска, используемый во всех логах и артефактах.

В конструкторе:

1. Сохраняются `config` и `run_id` в атрибуты экземпляра.
2. Инициализируется структурированный логгер, связанный с текущим пайплайном и запуском (минимальный контекст: `run_id`, имя пайплайна`).
3. Инициализируется внутренний реестр клиентских объектов (например, `_clients: dict[str, Any]`), которые должны быть корректно закрыты по окончании работы.

Рекомендуемое свойство:

- `pipeline_name: str` — читаемое имя пайплайна, по умолчанию совпадает с именем класса, но может браться из конфигурации.

## 4. Методы жизненного цикла

### 4.1. `extract` (абстрактный)

```python
extract(*args, **kwargs) -> pd.DataFrame
```

Извлекает сырые данные из внешних источников (БД, API, файлы и т.п.).

Требования:

- не выполняет запись данных на диск;
- возвращает данные в виде `pd.DataFrame`;
- полностью реализуется в наследниках.

### 4.2. `transform` (абстрактный)

```python
transform(df: pd.DataFrame) -> pd.DataFrame
```

Выполняет бизнес-трансформации и подготовку данных к валидации/записи:

- очистка и нормализация;
- обогащение по справочникам;
- дедупликация и агрегация.

Не взаимодействует с внешними хранилищами; реализуется в наследниках и получает на вход результат `extract`.

### 4.3. `validate` (базовая реализация поверх Pandera)

```python
validate(df: pd.DataFrame) -> pd.DataFrame
```

Проверяет качество и структуру данных с использованием `pandera`.

Логика по шагам:

1. Получение Pandera-схемы (`pa.DataFrameSchema`) из пайплайна:
   - через свойство/метод (например, `self.validation_schema`);
   - либо из `config`, если она там определена.

2. Если схема не задана:
   - залогировать предупреждение;
   - вернуть `df` без изменений.

3. Если схема есть:
   - выполнить `schema.validate(df, ...)`;
   - при необходимости привести порядок колонок к порядку, заданному схемой;
   - добавить служебные hash-колонки для детерминированной идентификации строк.

Добавление хэш-колонок выносится во вспомогательный защищённый метод:

```python
_add_hash_columns(df: pd.DataFrame) -> pd.DataFrame
```

Наследники могут:

- переопределять набор колонок, участвующих в хэше;
- переопределять стратегию хеширования (по бизнес-ключу, по всей строке и т.п.);
- при необходимости полностью переопределять `validate`, если требуется нестандартная логика.

С точки зрения общих абстракций, эта стадия соответствует применению `ValidatorABC` к табличным данным и выдаче результата, в котором DataFrame считается прошедшим валидацию.

### 4.4. `write` (базовая реализация)

```python
write(df: pd.DataFrame, output_path: Path) -> WriteResult
```

Сохраняет результат пайплайна на диск и генерирует метаданные.

Обязанности:

1. **Сортировка данных**  
   Перед записью строки сортируются по списку колонок, который задаётся:
   - конфигурацией пайплайна;
   - либо методом/свойством базового класса (например, `get_sort_columns()`).

2. **Определение формата**  
   Формат файла определяется по расширению `output_path`:

   - `.csv` — запись в CSV;
   - `.parquet` / `.pq` — запись в Parquet;

   При неизвестном расширении выбрасывается ошибка.

3. **Атомарная запись**

   - создать директорию `output_path.parent` (если её нет);
   - сформировать временный путь рядом с целевым файлом (`*.tmp`);
   - записать данные во временный файл;
   - после успешной записи переименовать временный файл в итоговый.

   Это гарантирует, что на диске либо нет файла, либо есть полноценно записанный результат.

4. **Генерация `meta.yaml`**

   Рядом с основным файлом создаётся `meta.yaml`, содержащий:

   - `run_id`;
   - имя пайплайна;
   - путь к результату;
   - формат файла;
   - количество строк;
   - временные метки начала и окончания стадии `write`;
   - длительность стадии;
   - флаг `dry_run` (для `write` всегда `False`);
   - список хэш-колонок (если применимо).

5. **Формирование результата**

   Возвращается `WriteResult` с минимум:

   - путём к итоговому файлу;
   - путём к `meta.yaml`;
   - форматом (`csv` или `parquet`);
   - количеством строк;
   - длительностью записи.

### 4.5. `run` (оркестратор)

```python
run(output_path: Path, *args, dry_run: bool = False, **kwargs) -> RunResult
```

Запускает полный цикл пайплайна и собирает метрики.

Шаги:

1. Логирование старта пайплайна, фиксация времени начала.
2. Последовательный вызов стадий:
   - `extract(*args, **kwargs)`;
   - `transform(df)`;
   - `validate(df)`.

3. Если `dry_run = True`:
   - залогировать факт пропуска записи;
   - `write` не вызывать;
   - `write_result = None`.

4. Если `dry_run = False`:
   - вызвать `write(df, output_path)`;
   - получить `WriteResult`.

Для каждой стадии измеряется длительность и количество строк; данные складываются в словарь метрик.

Метод обёрнут в `try/finally`, чтобы в `finally` гарантированно вызвать `close_resources`. При исключениях:

- логируется ошибка с привязкой к текущей стадии;
- исключение пробрасывается дальше.

`RunResult` содержит:

- `run_id`;
- имя пайплайна;
- флаг `dry_run`;
- длительность по стадиям и общую;
- количество строк после каждой стадии;
- `write_result` (или `None`).

## 5. Логирование

Используется `structlog`. Логгер создаётся в конструкторе и получает контекст:

- `run_id`;
- имя пайплайна.

Для стадий дописываются:

- `stage` (`"extract"`, `"transform"`, `"validate"`, `"write"`, `"run"`);
- `duration_sec`;
- `row_count` (если применимо).

Ключевые события:

- старт/окончание стадии;
- пропуск записи в режиме `dry_run`;
- пропуск валидации при отсутствии схемы;
- ошибки стадий (`logger.exception`).

## 6. Управление ресурсами

### 6.1. `register_client`

```python
register_client(name: str, client: Any) -> None
```

Регистрирует внешние ресурсы (подключения к БД, HTTP-клиенты, пул соединений и т.п.) во внутреннем реестре.

### 6.2. `close_resources`

```python
close_resources() -> None
```

Закрывает все зарегистрированные ресурсы в конце работы:

- для каждого клиента вызывается `close()` или `dispose()` (если есть);
- ошибки логируются, но не прерывают цикл;
- ресурсы удаляются из реестра;
- метод вызывается из `run` в блоке `finally`.

## 7. Результирующие типы: `WriteResult` и `RunResult`

Описываются отдельными датаклассами в `src/bioetl/types.py`:

- `WriteResult`:
  - путь к файлу данных;
  - путь к файлу метаданных;
  - формат;
  - количество строк;
  - длительность записи;
  - дополнительные поля при необходимости.

- `RunResult`:
  - `run_id` и имя пайплайна;
  - флаг `dry_run`;
  - метрики времени по стадиям;
  - количество строк после каждой стадии;
  - `write_result` (или `None`).

## 8. Связь с абстрактной библиотекой

На уровне абстракций:

- стадии описываются через `StageABC`;
- источники и парсеры через `SourceClientABC`, `RequestBuilderABC`, `ResponseParserABC`, `PaginatorABC`;
- валидация через `SchemaProviderABC` / `ValidatorABC` / `ValidationResult`;
- вывод через `WriterABC` / `MetadataWriterABC` / `PathStrategyABC`;
- инфраструктура через `ErrorPolicyABC`, `ProgressReporterABC`, `LoggerAdapterABC`, `TracerABC` и т.п.

`bioetl.core.PipelineBase` связывает эти концепции в конкретный, DataFrame-ориентированный сценарий и может рассматриваться как прикладная реализация универсальной оркестрации для табличных данных.
